# ghcast — визуальные доказательства из CLI в GitHub

> Статус: план, ревизия 2. Название `ghcast` — рабочее, не финальное.
> Дата: 2026-08-16.

## Контекст

Агент делает фичу во фронтенде. Результат его работы визуальный, а отчитаться он может только текстом:
«готово, проверил». Ревьюер в PR видит утверждение, а не доказательство. В обратную сторону то же —
баг вёрстки проще показать пятью секундами видео, чем описать абзацем.

Единственный существующий способ показать — перетащить файл в веб-интерфейс GitHub руками.
Публичного API для вложений у GitHub нет и, судя по [cli/cli#13256](https://github.com/cli/cli/issues/13256)
и [community#28219](https://github.com/orgs/community/discussions/28219), это осознанное решение (антиспам).

Три куска головоломки уже лежат готовыми — не хватает моста между ними. Инструмент = этот мост.

## Что наблюдалось

Ниже — **единичные наблюдения**, а не установленная семантика эндпоинта. Каждая строка воспроизводилась
один раз, на одной конфигурации. Интерпретации кодов ответа в правой колонке — гипотезы, которые
проверяет этап 0.

| Наблюдение | Как получено | Результат |
| --- | --- | --- |
| `uploads.github.com/user-attachments/assets` принял `gh auth token` | POST с `Authorization: Bearer $(gh auth token)`, токен `gho_` | `HTTP 201`, вернул `github.com/user-attachments/assets/<uuid>` |
| Ссылка инертна до цитирования | GET сразу после загрузки | `404`; после вставки в тело issue — рендерится |
| Картинка рендерится как `<img>` | `gh issue create --body "![t](URL)"`, затем `body_html` | `<img src="private-user-images...?jwt=">` |
| Видео рендерится нативным плеером | голый URL на своей строке | `<video src=...>` внутри `<details>` |
| PNG в репозиторий с read-доступом | `cli/cli` | `404 Not Found` — **гипотеза**: нужен push-доступ |
| `.txt` в свой репозиторий | — | `422`, два разных сообщения сразу: `content_type is not included in the list of allowed content types` **и** `name has a file extension that does not match the content type` |
| Токен утекает в argv | `/proc` без `hidepid`, `cmdline` режим 444 | подтверждено — снимается отказом от `curl` в пользу нативного HTTPS-клиента |
| `.webm` — поддерживаемый GitHub формат | [docs.github.com/attaching-files](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files) | да, наравне с `.mp4`/`.mov` |

**Коды ответа неоднозначны.** `404` может означать отсутствие push-доступа, но также неверный
`repository_id`, отозванный токен или снятый эндпоинт. `422` может означать неподдерживаемый MIME,
но также расхождение расширения с заявленным типом — оба сообщения пришли в одном ответе.
Поэтому диагностика строится по **коду вместе с телом ответа**, а не по коду, и обязательно имеет
терминальную ветку `endpoint_unavailable` для всего, что не разобрано.

Лимиты GitHub (из документации): **10 МБ** картинки и gif, **10 МБ** видео на бесплатном плане,
**100 МБ** видео на платном, **25 МБ** прочие файлы.

Для масштаба: скринкаст 8.7 с при 1000×620 — 238 КБ в WebM, 38 КБ после конвертации в mp4 (h264, crf 30).

## Что строим

CLI + skill в одном репозитории.

### Поверхность CLI — MVP

```
ghcast upload <file...> [--repo owner/name]
ghcast attach <file...> --to pr:42 | issue:42 | pr
```

`upload` печатает URL (или markdown с `--md`) и годится для пайпов.
`attach` загружает и **создаёт или обновляет комментарий, принадлежащий инструменту** — всегда,
без вариантов. Правка тела issue/PR и адресация `comment:<id>` **из MVP исключены**: без
compare-and-swap на стороне GitHub они молча затирают чужие правки.

Форма `pr` выводит номер из текущей ветки; если PR ещё нет — см. решение 9.

Общие флаги: `--caption`, `--key`, `--dry-run`, `--json`, `--no-convert`, `--allow-public`.

Во вторую итерацию: `report` (сводка по упавшим визуальным тестам), `compose` (склейка изображений).

### Модули

| Модуль | Ответственность |
| --- | --- |
| `target` | разбор `pr:N` / `issue:N` / `pr`; вывод репозитория и номера из ветки; определение видимости репозитория |
| `mime` | расширение → content_type по **allowlist GitHub**, не по системному `file`; предвалидация размера |
| `convert` | WebM → mp4 через `ffmpeg`; очистка метаданных; мягкая деградация; `--no-convert` |
| `digest` | `sha256(исходные байты) + id профиля конвертации` → стабильный ключ файла |
| `upload` | нативный HTTPS-клиент; разбор кода **и тела**; никаких автоповторов |
| `ledger` | реестр `digest → URL` внутри маркера комментария; переиспользование уже загруженного |
| `render` | markdown по типу: image → `![]()`, video → голый URL на своей строке |
| `comment` | поиск своего комментария по маркеру, создание или обновление |
| `harvest` | (итерация 2) обход `test-results/**`, группировка `-actual` / `-expected` / `-diff` |

### Коды возврата

| Код | Значение | Что делает агент |
| --- | --- | --- |
| 0 | успех | продолжает |
| 2 | неверные аргументы | чинит вызов |
| 3 | `target_not_found` — PR/issue не существует | **спрашивает пользователя**, не выдумывает |
| 4 | `partial_upload` — часть файлов загружена, цель не тронута | показывает список загруженных URL пользователю |
| 5 | `endpoint_unavailable` — ответ не разобран, состояние неизвестно | **не повторяет**, докладывает |
| 6 | `refused_public` — публичный репозиторий без явного согласия | спрашивает подтверждение |
| 1 | прочая ошибка | докладывает |

## Skill

**Скилл один**, многофайловый — короткий `SKILL.md` всегда в контексте, тяжёлые части в `references/`
подгружаются по необходимости. Та же схема, что у `playwright-cli`. Стиль изложения — как в
`~/.claude/commands/qa-handoff.md`: таблицы, явный разбор аргументов, явная обработка отказов.

Отдельного скилла «для тестирования» не делаем. Проверено: установленный `playwright-best-practices`
содержит `testing-patterns/visual-regression.md` на 634 строки — маскирование волатильного контента,
отключение анимаций, пороги, CI в докер-образе, адаптивность, компонентные снапшоты, обновление
эталонов, кросс-браузерность, антипаттерны и семь сценариев troubleshooting. Знание о том, *как писать
визуальные тесты*, покрыто целиком; второй скилл на ту же тему только конкурировал бы за триггер.

Существующий скилл заканчивается там, где дифф уже посчитан, а три PNG легли на диск — в
`test-results/` локально или в zip-архив прогона в CI (строка 220 его конфига: `uses: actions/upload-artifact@v4`).
Ни туда, ни туда никто не заходит. **Наша дельта — ровно этот последний шаг до глаз ревьюера.**

Раз CI вне области видимости (решение 5), сценарий итерации 2 такой: тесты прогоняет локально
разработчик или агент, а инструмент забирает артефакты из `test-results/` и постит.

### Принцип наполнения

Скилл не пересказывает `--help` — это агент прочитает сам, и такой скилл устареет на первом релизе.
В скилл идёт только то, что агент делает неправильно, если ему не сказать.

### `SKILL.md`

Описание во frontmatter формулируется через ситуацию, а не через инструмент — именно оно решает,
сработает скилл или нет:

```yaml
description: Приложить визуальное доказательство к issue или PR — скриншот вёрстки,
  видео сценария, до/после. Использовать, когда изменение или баг видно глазами,
  а текстом описывается плохо.
```

Одиннадцать разделов — по числу мест, где агент ошибается без подсказки:

1. **Прикладывать или нет.** Частый провал в обе стороны: либо никогда, либо видео в каждый PR.
   Таблица решения: вёрстка и статичный экран → скриншот; поток, интеракция, анимация → видео;
   отличие до/после → два скриншота рядом; бэкенд, рефакторинг, конфиги → ничего.
   Явным текстом: видео стоит ревьюеру минуту внимания, скриншот — секунду. По умолчанию скриншот.
2. **Снимать на санитизированных данных.** Это основной механизм защиты, а не маскирование.
   Демонстрационный сценарий гоняется на тестовом аккаунте и фиктивных данных; продовые данные
   в кадре — дефект сценария, а не повод замазать.
3. **Маска — вторая линия, и она дырявая.** `mask` у Playwright закрывает область в момент съёмки,
   но видео прокручивается и меняет layout: то, что было закрыто на первом кадре, откроется на пятом.
   Правило: маска для статичных скриншотов, для видео — санитизированные данные плюс проверка
   финального файла глазами.
4. **Обязательный просмотр перед отправкой.** Агент открывает готовый файл (скриншот читается
   напрямую; для видео — извлечь кадры) и убеждается, что в кадре нет токенов, почт, имён клиентов.
   Публикация без просмотра запрещена.
5. **Как записать смотрибельный сценарий.** Агент пишет скрипты под скорость и получает двухсекундную
   нечитаемую кашу. Предписать: пауза 700 мс в начале; `pressSequentially` с `delay: 60` вместо `fill`;
   `waitForTimeout` между шагами; `showChapter()` на смысловых переходах; вьюпорт 1000–1280 по ширине,
   не 1920 — иначе текст в плеере нечитаем.
6. **Аннотации требуют предварительного шага.** `showOverlay` с рамкой вокруг элемента нуждается в
   `boundingBox()`, тот — в локаторе, тот — в снапшоте. Сам агент эту цепочку не выстроит и аннотациями
   просто не воспользуется. Даётся готовым куском кода.
7. **Ссылка не работает сразу — и это нормально.** URL отдаёт `404`, пока его не процитируют.
   Без предупреждения агент «проверит» результат, получит 404 и уйдёт в цикл перезагрузок.
8. **Отказы: разбирать код возврата, не HTTP-код.** Таблица кодов выше. Ключевое:
   `endpoint_unavailable` (5) и `partial_upload` (4) **никогда не повторять автоматически** —
   сервер мог принять файл, а ответ потеряться, и повтор создаст дубль.
9. **Нет PR или issue — спросить, а не выдумывать.** Код 3. Агент не создаёт PR молча и не подставляет
   соседний номер: задаёт вопрос через `AskUserQuestion` (создать PR / приложить к существующему
   issue / сохранить файл локально и отдать путь).
10. **Публичный репозиторий — отдельное согласие.** Код 6. Агент не подставляет `--allow-public`
    сам: спрашивает пользователя, предварительно сказав, что загруженный файл отозвать нельзя.
11. **Скриншот как обратная связь себе.** Агент может прочитать картинку, которую только что снял, —
    увидеть свою работу вместо догадок по DOM-снапшоту. Это про самопроверку, а не про коммуникацию.

### `references/visual-reports.md` — содержание

Не пересказ визуального тестирования, а решения про доставку:

- **Что постить.** Дифф в один-два пикселя от сглаживания — не находка, а повод настроить `threshold`;
  скилл отправляет в `playwright-best-practices`, а не постит шум в PR.
- **Как не завалить PR стеной картинок.** Десять упавших снапшотов — это тридцать изображений.
  Формат: таблица-сводка сверху, каждый снапшот в свёрнутом `<details>`. При большом числе снапшотов
  дешевле склеить контактный лист, чем грузить по три файла на каждый (лимит 10 МБ на изображение).
- **Когда не постить вообще.** PR из одного обновления эталонов — там «изменилось всё» по определению.
- **Соглашение об именах артефактов.** Где Playwright их кладёт и как группировать
  `-actual` / `-expected` / `-diff` обратно в один снапшот.

### Правило ссылок наружу

Ссылаться на соседние скиллы **по имени** (`playwright-cli`, `playwright-best-practices`), а не по пути
в файловой системе — на другой машине путь будет другой, а имя то же.

## Решения

### Принято

1. **Не строим свой движок записи.** `playwright-cli` покрывает capture и аннотации лучше, чем самописное.
   Инструмент принимает готовые файлы с диска.
2. **Нативный HTTPS-клиент вместо `curl`.** Мы всё равно в Node — внешний процесс не нужен, а вместе
   с ним исчезает и весь класс утечек через argv. `gh` остаётся зависимостью только для `gh api`
   (резолв цели, работа с комментариями) и разрешения токена.
3. **Матрица авторизации зафиксирована и узкая.** MVP читает `GH_TOKEN`, затем `gh auth token`.
   **`GITHUB_TOKEN` намеренно не читается**: он обычно приходит из Actions, а CI вне области видимости,
   и поведение эндпоинта с installation-токеном (`ghs_`) не проверялось. Молча подхватить непроверенный
   токен хуже, чем не найти токен вовсе. Статус в документации — unsupported.
4. **Токен не должен утечь ни в один канал.** `ffmpeg` запускается **до** получения токена и с
   очищенным окружением, чтобы дочерний процесс его не унаследовал. Проверяется тестами: токена нет
   в argv, stdout, stderr, JSON-выводе и debug-логах.
5. **CI вне области видимости.** Локальный запуск с `gho_`-токеном от `gh auth login`. Следствие:
   визуальные отчёты итерации 2 запускаются руками или агентом, а не из workflow.
6. **Загрузка отделена от прикрепления.** `upload` печатает URL и годится для пайпов; `attach` — для агента.
7. **`attach` работает только через собственный комментарий.** Правки тела и `comment:<id>` исключены
   из MVP: без compare-and-swap они молча затирают чужие изменения.
8. **Видео по умолчанию конвертируется в mp4.** Причина не только в лимите: `playwright-cli` отдаёт
   WebM/VP8, который Safari проигрывает непредсказуемо, а mp4/h264 играет везде. Экономия попутная,
   но крупная — в замере 238 КБ → 38 КБ. Конвертация заодно **срезает метаданные**. Деградация мягкая:
   если `ffmpeg` не найден, грузим WebM как есть с предупреждением, и падаем с внятной ошибкой только
   если файл при этом не влезает в лимит. `ffmpeg` — рекомендуемая зависимость, не обязательная.
   Флаг `--no-convert` для обхода.
9. **Нет PR или issue — спрашиваем пользователя.** Код возврата 3, CLI ничего не создаёт сам.
10. **Публичный репозиторий требует явного согласия.** `attach` определяет видимость до загрузки;
    для публичного нужен `--allow-public`, иначе код 6. Загруженный файл отозвать нельзя, поэтому
    согласие спрашивается **до** отправки, а не после.
11. **Никаких автоповторов после таймаута и `5xx`.** POST мог быть принят сервером, а ответ потерян;
    повтор создаст второе вложение. Такие случаи получают код 5 и передаются человеку.
12. **Частичный успех — отдельный контракт.** Все файлы сначала валидируются и конвертируются, и только
    потом загружаются. Если упала загрузка третьего из пяти: цель **не изменяется вообще**, код 4,
    в JSON перечислены уже созданные URL, exit status ненулевой.
13. **Фолбэка на релизы в MVP нет.** Нужен ровно для двух случаев: чужой репозиторий без push-доступа
    и не-медиа файлы. Инструмент про визуальные доказательства в своих репозиториях, так что вместо
    фолбэка — внятная ошибка. Если понадобится позже: **один переиспользуемый релиз** с фиксированным
    тегом (потолок 1000 ассетов), а не релиз на PR — тогда вопрос уборки не возникает.

### Идемпотентность — что именно гарантируется

Двухуровневая, и уровни надо называть раздельно, иначе гарантия звучит сильнее, чем она есть.

**Уровень 1 — представление.** В комментарий пишется маркер `<!-- ghcast:v1:<kind>:<key> -->`.
При повторе комментарий с тем же маркером обновляется, а не создаётся новый.

- `key` по умолчанию выводится из вида команды и цели; переопределяется `--key`.
- Поиск ведётся **только среди комментариев текущего пользователя** (логин берётся из `gh api user`).
- Найдено несколько маркеров — берётся самый старый, остальные перечисляются в выводе как аномалия;
  инструмент их не удаляет.

**Уровень 2 — загрузка.** Без дедупликации каждый повтор создавал бы новое вложение, а старое
осталось бы висеть неудаляемым. Поэтому в маркер вкладывается реестр `digest → URL`, и при совпадении
digest загрузка **пропускается**, переиспользуется существующий URL.

- `digest = sha256(исходные байты) + идентификатор профиля конвертации`. Считается по **исходнику**,
  а не по результату `ffmpeg`: вывод кодировщика не побитово стабилен между версиями.

**Что не гарантируется.** Два параллельных запуска на одну цель могут оба не найти маркера и создать
по комментарию. Блокировки нет. Смягчение — перечитать цель непосредственно перед записью, но гонку
это сужает, а не устраняет. Формулировать честно: идемпотентность при последовательных запусках.

## Этапы

### Этап 0 — снять семантику эндпоинта (перед кодом)

Одного успешного запроса недостаточно. Матрица наблюдений; каждая ячейка — код ответа **и тело**:

**Цели публикации**
- тело issue, комментарий к issue, тело PR, комментарий к PR, комментарий к review.
  Проверить, что `user-attachments` URL активируется во всех четырёх, а не только в теле issue.

**Видимость репозитория**
- приватный и публичный: активация ссылки, доменное имя в отрендеренном HTML
  (`private-user-images` против публичного), доступность анонимному запросу.

**Токены**
- `gho_` (`gh auth login`) — база.
- classic PAT `ghp_` с `repo` и без него.
- fine-grained PAT с минимальным набором прав — выяснить, какое право реально требуется.
- `ghs_` из Actions — только зафиксировать результат, поведение вне scope.

**Типы и размеры**
- `.webm`, `.mp4`, `.png`, `.gif`, `.svg` — какие проходят.
- превышение лимита: какой код, какое тело, на каком этапе (до или после отправки тела запроса).
- расхождение расширения и `content_type` — воспроизвести оба сообщения `422` раздельно.

**Отказы и неопределённость**
- поведение при разрыве соединения после отправки тела: принял сервер файл или нет.
  Это определяет, можно ли вообще когда-либо повторять — предварительный ответ «нельзя».
- ответ на заведомо неверный `repository_id` — отличается ли `404` от случая без push-доступа.
  Если не отличается, диагностика обязана говорить «либо нет доступа, либо репозиторий не найден»,
  а не утверждать одно из двух.

**Результат этапа:** таблица «код + признак в теле → код возврата CLI», включая ветку
`endpoint_unavailable` для всего неразобранного. Она становится спецификацией модуля `upload`.

### Этап 1 — мост

- Каркас пакета по образцу `easy-plan`: TS + ESM, pnpm, vitest, eslint, `bin` в `package.json`.
- `mime` с allowlist GitHub из документации, не из системного `file`.
- `convert`: WebM → mp4 (`-c:v libx264 -crf 30 -pix_fmt yuv420p -movflags +faststart -an`
  плюс срезание метаданных), запуск до получения токена и с очищенным окружением.
- `digest` + `ledger`: пропуск загрузки при совпадении.
- `upload`: нативный HTTPS, таблица из этапа 0, ноль автоповторов.
- `target`: разбор цели, определение видимости, код 3 при отсутствии PR/issue.
- `comment`: поиск своего комментария по маркеру, создание или обновление.
- `render`: markdown по типу контента.
- Пакетная семантика: валидация и конвертация всех файлов до первой загрузки, код 4 при частичном успехе.
- `SKILL.md` + `references/`.

### Этап 2 — визуальные отчёты

- `harvest` артефактов Playwright и `report`: один комментарий с таблицей было / стало / дифф.
- `compose`: до/после рядом, матрица вьюпортов одним листом.
- Возможные продолжения: прогон сценария на base и head для визуального сравнения ветки;
  видео именно упавшей попытки при ретрае; доказательство acceptance criteria по пунктам.

## Проверка

**Модульно (vitest):**
разбор `<target>` во всех формах; расширение → content_type; markdown по типу контента;
таблица «код + тело → код возврата», включая неразобранный ответ → `endpoint_unavailable`;
поиск и замена блока по маркеру; расчёт `digest` и переиспользование URL из реестра;
поведение при нескольких найденных маркерах.

**Утечка токена (обязательный набор):** после вызова с подставным токеном его нет в argv дочерних
процессов, stdout, stderr, JSON-выводе и debug-логах; окружение `ffmpeg` не содержит токена.

**Интеграционно, на приватном репозитории** (для CI самого пакета — выделенный тестовый репозиторий
с секретом либо записанные HTTP-фикстуры; решить при написании тестов):

1. `--dry-run` — печатает план, ничего не трогает.
2. Без `--dry-run` — комментарий появляется, `body_html` содержит `<img>`.
3. **Повторный тот же вызов** — комментарий обновлён, второго нет, **новое вложение не создано**
   (проверяется по совпадению URL с предыдущим запуском).
4. Повтор с изменённым файлом — URL новый, комментарий тот же.
5. `.webm` — конвертируется в mp4, `body_html` содержит `<video>`; с `--no-convert` грузится WebM.
6. `.log` — внятная ошибка про неподдерживаемый тип с текстом из тела ответа.
7. `--repo cli/cli` — сообщение «нет доступа либо репозиторий не найден», без ложной уверенности.
8. `--to pr` на ветке без PR — код 3, сообщение, ничего не создано.
9. Публичный репозиторий без `--allow-public` — код 6, загрузки не было.
10. Пять файлов, из которых третий заведомо негодный — цель не изменена, код 4, в JSON перечислены
    загруженные URL.
11. Убрать за собой: удалить тестовые issue и комментарии.

**Сквозной сценарий:** записать демо через `playwright-cli` (`video-start` → `run-code` со сценарием
и главами → `video-stop`), просмотреть файл, приложить к PR, открыть PR и убедиться, что плеер играет.

## Риски

- **Модель угроз публикации: загруженное считать неотзываемым.** CLI **не гарантирует** удаление уже
  загруженного файла. Удаление markdown из комментария не убирает вложение — оно остаётся доступным
  по своему URL. Отсюда порядок защиты: санитизированные данные (основное) → маска для статичных
  кадров (вспомогательное) → обязательный просмотр финального файла → явное согласие на публичный
  репозиторий **до** отправки. Маска сама по себе недостаточна: видео прокручивается и меняет layout,
  закрытое на первом кадре открывается на пятом.
- **Семантика эндпоинта не установлена.** Все интерпретации кодов — гипотезы до этапа 0. Диагностика
  проектируется так, чтобы неразобранный ответ давал `endpoint_unavailable`, а не ложное объяснение.
- **Эндпоинт недокументирован.** Публично о bearer-авторизации написали в августе 2026; GitHub может
  закрыть его без предупреждения. Фолбэка в MVP нет (решение 13), инструмент умрёт вместе с эндпоинтом.
  Принято сознательно: восстановление — добавление одного маршрута, а не переписывание.
- **Неопределённость после таймаута.** Принял сервер файл или нет — узнать нельзя. Отсюда запрет на
  автоповтор и код 5 вместо попытки «починить» ситуацию самостоятельно.
- **Гонка при параллельных запусках.** Два одновременных `attach` на одну цель создадут два
  комментария. Блокировки нет, гарантия ограничена последовательными запусками.
- **Видимость наследуется от репозитория.** В приватном репо ссылка открывается только участникам.
  Это правильное поведение, но скилл обязан это сказать, иначе агент пообещает «публичную ссылку».
- **Аннотации требуют локаторов.** `showOverlay` с рамкой вокруг элемента нуждается в `boundingBox()`,
  то есть агент должен сначала снять снапшот и найти элемент. Это шаг сценария, а не опция инструмента.
